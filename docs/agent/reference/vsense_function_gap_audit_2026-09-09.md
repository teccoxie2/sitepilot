# Vsense 奥克兰开发核算台：功能差距核查

核查日期：2026-09-09。目标站点：[demo-cost.vsense.co.nz](https://demo-cost.vsense.co.nz/)。

当前公开实现已经形成「选址初筛 + 有来源的造价 + V2 图纸取量/审核/报价版本」工作台。对照此前讨论的奥克兰房地产开发全流程，主要待建设范围是：正式项目和资料管理、可研与资金、预算批准、招采与实际成本、施工、许可交付、销售和复盘。

本次按 60 个业务功能与上线验收项建立比较口径：**14 项已见实现证据、9 项部分具备、33 项公开端未见、4 项待核实。** 因此目前的候选待补齐范围为 **42 项（9 项补强 + 33 项待确认是否需要新建）**，另有 4 项需进一步验证。这不是后台全部功能的最终盘点，也不是完成率或工期估算。

## 核查口径与证据边界

- 60 项是依据此前讨论建立的产品验收清单，包含业务能力和上线质量要求；不是某个行业标准，也不是页面、按钮或成本科目数。不同项目删减范围后应重新计数。
- 已检查主页、旧版图纸取量、V2 列表，以及公开可加载的选址详情/V2 详情前端资源；另验证了地址搜索、当前会话空项目列表及两类模型就绪的只读接口。
- 网页搜索工具未成功抓取本站正文；随后通过直接 HTTP 取得公开 HTML、页面加载的 JavaScript 及上述只读响应。未把无关搜索结果当作证据。
- 未登录成员账号，未使用私人项目 ID，未上传文件、建立项目、生成报价或执行审核/修正/导出。详情页通过不存在的审计标识读取通用页面外壳和公开资源；没有访问其他人的实际项目。
- 「已见实现证据」表示有页面/前端处理/接口调用路径，通常还没有通过完整业务验收。少量接口实际返回成功也不证明其他写入接口可用。
- 「公开端未见」是候选差距，不能推断后台一定没有实现；「待核实」主要用于公开页面不足以判断的运行质量要求。不得把「已见」计作 100% 完成，把「部分」机械计作 50%。

## 已有能力应保留

1. 议会地址选择及地块/区划/坡度/航拍的来源展示，正式 LIM 文字层入口。
2. 方案对比和按套数、层数、户型、面积调整的初步核算。
3. V2 的 PROJECT、DOCUMENTS、TAKEOFF、REVIEW、ESTIMATE、HISTORY 六个工作区标签。
4. 图纸清单、分页图像、证据框、取量公式及从工程量回看来源。
5. 数量/单位/科目的人工修正、原因记录，以及接受/拒绝/未解决的审核队列。
6. 绑定图纸集与价表的报价版本、历史金额冻结提示，以及携带 estimate_id 的 CSV/JSON 导出。
7. 未计价原因、范围/价格完整度展示。维持明确列缺项的做法，继续补足覆盖范围。

这些是从当前发布的前端代码与公开页面得到的证据，不能重列为「从零开发」。Dify 是否接入也不能代替对现有流程的运行验收。

## 先把取量报价工具做成可持续使用的产品

如果近期目标是让 QS 或开发团队稳定使用取量与报价功能，建议先安排以下 8 个工作包。它们是上面清单的组合，不另加进 60 项，也不代表其他已见功能已经免验收。

| 顺序 | 工作包 | 对应项 | 完成判据 |
|---|---|---|---|
| 1 | 统一项目及单元关系 | A06 | 从选址进入同一项目的图纸、报价和后续业务，记录显式关联；名称相同不会误合并。 |
| 2 | 资料长期保存与恢复 | C05、J02、J06 | 换设备及服务重启后，原件、证据、修正和旧报价仍完整；重复恢复不重复生成正式数量。 |
| 3 | 图纸目录与修订控制 | C02、C04 | 可人工补 Drawing Index；旧版、有效版和适用范围清楚，缺图有明确责任与处理结果。 |
| 4 | 扫描图验收与人工补量 | D02、D03 | 用建筑/结构扫描图跑通：原件→可核对证据→确认数量；无法可靠识别时可人工补入。 |
| 5 | 工程报价和主要工种覆盖 | D06、E04、E05 | 先选择目标住宅类型补齐必要范围；供应商工程报价有单位、日期和包含范围，未知值不冒充已确认总价。 |
| 6 | 正式预算批准与发布 | E06 | 审核完成后可批准明确报价版本；修改产生新预算修订，不覆盖旧批准记录。 |
| 7 | 成员权限与操作责任 | J01、J03 | 团队成员按项目角色操作，关键修改和批准可追踪到人。 |
| 8 | 关键流程与计算回归验收 | J04、J05、J06，并覆盖已有功能 | 验证数量修正、费率变化、历史冻结、导出依据、错误恢复；能追踪每次识别的时间和费用。 |

不宜仅凭公开端检查给这些工作包承诺人天或报价。是否已有数据库、后台队列、对象存储和权限系统，会明显改变实际开发量。

## 再扩展全流程

- 第一段业务扩展：批准预算 → 询价/采购与分包 → 收货/计量 → 实际成本 → 预计完工成本，并接入工作包与现场变更。
- 第二段业务扩展：土地尽调、开发可研与月度资金、RC/BC 条件及检查资料、CCC/产权节点、销售结算和售后复盘。
- 两段可以按试点项目阶段并行安排；没有必要强迫真实开发过程变成一条固定顺序。
- 继续保留现有界面和取量引擎。采购、财务、项目权限等通用能力可评估接入此前研究的 ERPNext/Frappe；先确定正式业务数据由哪一套系统负责。
- Dify 的接入价值是管理需要频繁调整的模型流程、检索和人工处理节点。本站已经有模型调用与审核流程的公开证据；新增 Dify 不会自动补齐采购、预算、许可或销售功能，也不应成为完成这些业务功能的先决条件。

## 需要特别核实的现状

**资料恢复。** V2 明确依赖浏览器保存原件，并含引擎实例变化后的恢复逻辑；页面也提示演示容器重启可能丢失原图。公开代码中，工作区读取返回 404 时会提前报错，后面的本机原件恢复分支不会在这条路径继续执行。需要在授权测试环境区分「项目存在但 documents 为空」与「项目不存在」的恢复行为。这是静态代码发现的验收风险，本轮没有重启服务或实测丢失数据。

**人工目录维护。** 页面提示扫描件可能需要人工补 Drawing Index，但当前公开工作区代码没有相应编辑控件或保存调用。应核实是否另有管理入口；若没有，补齐可操作的流程。

**识别能力。** V2 的 /ready 实际返回 vision=true，因此不能说当前未配置视觉模型；但本轮未验证扫描图识别、旋转或证据坐标的准确性。旧版文字层页面的限制不能直接套用到 V2。

**正式预算。** 已有审核按钮与历史报价读取，但不能仅凭这些判定具备预算批准、权限控制、财务承诺和变更管理。应分别验收。

**金额含义。** 可见界面已展示未计价和完整度信息；选址页面还明确其金额是部分公开价格账单。进入正式报价、预算和采购前，需要约定缺项/暂估/排除范围及通过条件。
